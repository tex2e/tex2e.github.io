# 自己紹介サイト リニューアル設計案

作成日: 2026-09-20 / 状態: 初版実装済み・海のテーマに更新

## 最新方針：広くて深い電子の海

以下の当初案に対し、背景・色・図形は海のテーマへ更新した。

- 光が差す上層から深い青の海底へ、ページ全体を連続する水中空間として構成する。
- 乱数を不規則に漂う粒子、暗号を鍵、プロトコルを経路に沿う信号として表現する。背景には回路状の配線と接点を置き、自然の海より電子の海としての印象を優先する。
- フラクタルはSelected WorksのRecursive Tree Rendererカードで、写真の代わりとなる生成SVGとしてのみ使用する。背景や他の章には置かない。
- キャラクターの枠は六角形。使用する表情は `normal` / `thinking` のみ。
- 実績・プロフィールも深い青に統一する。初期案の紙色への切り替えは採用しない。
- `sample.png` は潜る視点と技術モチーフの参考とし、ページ背景への転載・複製はしない。
- 動きは停止ボタンで止められ、OSの動きを減らす設定でも停止する。


## 1. 設計の結論

コンセプトは **「見えないしくみを、わかる形に。」**。

乱数・暗号・プロトコルの探究を、まこ と てふの二人が案内する自己紹介ページにする。スクロールに伴い、同じ粒子や線が「散らばる粒子 → データのまとまり → 通信する線 → フラクタルの木」へと姿を変える。章ごとの別々の装飾ではなく、前の場面の形が次の場面につながる体験を目指す。

最優先は「誰で、何に強く、何を作ってきたか」が伝わること。演出を最後まで見なくても、冒頭からブログ・作品・プロフィールへ移動できる。

フラクタルの木は採用を推奨する。既存作品 Recursive Tree Renderer があり、本人の制作・関心に根拠のある象徴として使える。ただし木が暗号の安全性や通信手順を表すような説明はせず、数理的な好奇心を示す場面として扱う。

## 2. 調査で確認したこと

### 現行サイト

- `index.html` にプロフィール、資格、活動履歴、作品、連絡先がまとまっている静的サイト。
- まこは「執筆・発信担当」、てふは「実装・技術検証担当（中の人）」という役割がすでにある。この設定を引き継ぎ、二人の別人によるチームと誤解させない。
- Software Design の「乱数のひみつ」「暗号のひみつ」、RFC Trans、TLS 1.3 の実装、暗号の解説・実装など、テーマに直結する実績が豊富。
- 一方、資格と活動履歴の長い一覧が作品より先にあり、初めての訪問者が強みをつかむまでに時間がかかる。
- TLS の冒頭紹介と作品一覧では表現の範囲が異なる。新しい紹介では、現行の作品説明に合わせ「TLS 1.3の鍵共有・パケット暗号化をPythonで実装」など、実装範囲を明示する。完全なプロトコルスタック実装とは断定しない。
- ScrollMagic・TweenMax による写真のパララックスと登場演出がある。現行JSはタッチ端末で演出処理を終了する構成。
- 資格には過去の有効期間が記載されているものがある。取得・合格履歴と現在有効な資格は分け、更新状況を推測しない。

### キャラクター素材

- `image/characters/mako/normal.png` と `tefu/normal.png` を目視確認。どちらも1024×1024の透過PNGで、胸から上の人物像。
- まこ: 紺色の髪・服、緑の目とアクセント。てふ: 金色の髪・目、紺色の服。二人の共通色と差し色をページ全体に展開できる。
- 両者に `normal / thinking / proud / surprised / troubled / happy` と口の差分がある。表情差分の切り替え位置・輪郭の一致は実装前に確認する。
- 全身画像ではないため、歩行や木の下に立つような演出には使わない。画面下辺や紹介パネルから自然に現れる胸像として扱う。
- normal画像だけで約1.7MBある。全差分の初期読み込みを避け、表示寸法に応じた配信用画像を別途作成する。

### 参考サイト

参照: [And Idea / About](https://www.andidea.jp/about)

取得したページ内容では、大きな宣言から理念、事業領域、サービス、会社情報、問い合わせへ進む構成を確認した。参考にするのは、最初に印象を作り、続く章で具体的な内容を示す情報の順序。

この調査環境では実ブラウザーでスクロール時の動作を再生確認していない。固定時間、背景変化、イージングなどの具体的な動作は未確認。以下の演出は、参考サイトの実装を再現したものではなく、今回のテーマに合わせた独自提案である。

## 3. 訪問者と情報の優先順位

主な訪問者は、記事から著者に関心を持った読者、実装や技術に関心のあるエンジニア、執筆・登壇などの活動実績を確認したい人と想定する。

1. 冒頭で名前・専門領域・二人の役割を知る。
2. 三つのテーマと代表実績から、取り組みの具体像を知る。
3. 関心のある記事・コード・サービスに進む。
4. 必要なら活動履歴・資格・連絡先を確認する。

全履歴を削るのではなく、主な導線から詳細へと段階をつける。

## 4. ページの流れ

| 章 | 内容とコピー案 | スクロールで変わるもの | 実績・移動先 |
| --- | --- | --- | --- |
| 00 / Intro | 「見えないしくみを、わかる形に。」名前と「乱数・暗号・プロトコルを探究し、実装し、伝える。」 | 紺の背景に小さな粒子。二人の胸像を配置。下へ進むと人物が退き、粒子が次章の主役になる | 「探究と作品を見る」「ブログを読む」 |
| 01 / Randomness | 「予測できなさを、探究する。」 | 散らばる点を拡大し、ビットや小さな標本のまとまりとして見せる。画面全体の文字を乱雑に変え続けない | 連載「乱数のひみつ」 |
| 02 / Cryptography | 「秘密を守る、しくみをほどく。」 | 前章の点がデータブロックへまとまり、入力と出力の表現に変わる。短い装飾文字列だけが変化し、本文は固定 | 「暗号のひみつ」、暗号の解説・実装 |
| 03 / Protocols | 「約束を重ねて、通信になる。」 | ブロックが二つの通信端点の間を順序立てて移動し、接続を表す線が残る | RFC Trans、TLS 1.3の実装 |
| 04 / Fractal | 「単純な規則から、豊かなかたちへ。」 | 通信の線が一度抽象的な一本の線になり、幹、枝、細枝へと成長。少し引いて木の全体を見せる | Recursive Tree Renderer |
| 05 / Works & Writing | 「つくったもの。書いてきたこと。」 | 背景を明るい紙色へ。動きを減らし、作品と執筆実績を読む時間にする | 厳選作品・連載・全実績 |
| 06 / Profile & Contact | 二人の役割、経歴の要約、連絡先 | 木の小さなモチーフと二人が再登場。冒頭とのつながりを作る | 詳細履歴・GitHub・ブログ・既存連絡先 |

01〜03は、一つの共通した表示領域が三段階に変化する中核部分。すべての章を長時間固定する構成にはしない。04では木を大きく見せて視覚的な休止を作り、05以降は通常の読みやすいページに戻す。

冒頭の文字は演出完了を待たず表示する。技術分野を知らない人でも、主見出し・短い説明・作品名だけで内容を追えるようにする。

## 5. キャラクターの役割

使用する表情は `normal` と `thinking` の二種類に限定する。

二人はページの案内役。毎章の長い会話や常駐するチャットUIにはしない。

| 場面 | まこ | てふ | 目的 |
| --- | --- | --- | --- |
| 冒頭 | normal | normal | 名前と役割を最初に印象づける |
| 乱数 | thinking、小さな問いかけ | 必要に応じて小さく登場 | 読者の好奇心を代弁する |
| 暗号・プロトコル | 要点を伝える短い一言 | thinking、実装への一言 | 執筆と検証の役割を見せる |
| フラクタル | normal | normal | 数理への親しみを伝える |
| プロフィール | normal | normal | 正式な役割説明を読む |

台詞案は「予測できないって、どう確かめる？」「仕様を読んで、動かして確かめる。」程度の一文。本文を吹き出しに閉じ込めず、読ませる情報は通常のHTMLにする。台詞は人格や口調が未確定のため仮案。

口の差分は初版では使用しない。音声のない常時口パクは注意を奪いやすく、専門性を伝える目的への寄与が薄い。まず表情の切り替えだけで成立させる。

クレジットは現行にある「しろねこ 様」の情報を保持しつつ、新素材・各人物への正しい対応を確認して表記する。

## 6. 視覚デザイン

方向性は「静かな数理のアトリエ」。濃紺の空間、細い線、十分な余白と、人物の柔らかな表情を組み合わせる。

| 用途 | 色案 | 意図 |
| --- | --- | --- |
| 前半の背景 | `#111827` | 二人の服の紺色と統一する |
| 前半の本文 | `#F5F2E9` | 冷たすぎない白 |
| 乱数・まこ | `#B9DCAC` | 目と髪飾りに合わせた緑 |
| 暗号・てふ | `#D9BC78` | 髪や目に合わせた金 |
| プロトコル | `#8FBBD3` | 通信の線を識別する青 |
| 実績部分の背景 | `#F3F0E8` | 長い文章を読む紙のような面 |

色は役割の補助とし、識別には見出し・番号・形も使う。最終配色のコントラストは実装時に測定する。

見出しは大きな日本語サンセリフ、本文は読みやすい通常書体。英数字の小見出しやデータ表現だけ等幅にする。全面をターミナル風にせず、実績に進んだときは文章と画像が主役になる。

人物は背景との境界が失われないよう、背後に淡い面または柔らかな光を置く。強い発光や大きなドロップシャドウは避ける。胸像の下端は画面やパネルの端にそろえ、不自然な切り抜きに見せない。

## 7. スクロール演出の仕様案

- 標準スクロールを維持。ホイール操作の乗っ取り、強制的なページ送り、閲覧を待たせる導入は設けない。
- デスクトップでは01〜03の図形表示を短い区間だけstickyにし、横の説明が進むにつれ状態を変える。中核部分全体の高さはまず約300〜360svhで試し、読む速さを見て調整する。
- その区間の進行度を0〜1へ正規化し、粒子・ブロック・通信線の状態を補間する。戻りスクロールでも同じ位置では同じ形になる。
- フラクタルの成長は別区間で扱い、深さごとに枝が現れる。スクロールのたびに木を抽選し直さず、同一の種から生成した形を使用する。
- 小画面では固定演出を解除し、図形と説明を縦に並べる。章の登場に合わせて短く変化させ、横並びの人物で本文を圧迫しない。
- 画面の縦幅が短い場合もstickyを解除する。端末がタッチ操作かどうかだけでは分岐しない。
- 動きを減らす設定では変形・パララックスを止め、各章の完成状態を静止表示する。JSが動かなくても本文・画像・リンクを表示する。
- 装飾は読み上げ対象から外す。本文に復号風の文字置換をかけず、キーボード操作・文字選択・拡大表示を保つ。
- 常設ナビは「探究 / 作品・執筆 / プロフィール」とブログへのリンク。演出を経由せず各章へ進める。

技術表現は概念的な演出と位置づける。点が整列することを「安全な乱数になる」と説明したり、フラクタルの規則性を暗号の安全性と結びつけたりしない。実際のTLSメッセージ名・手順を使う場合は、仕様に照らして別途設計する。

## 8. フラクタルの木の扱い

木は画面いっぱいの森ではなく、まず一本を大きく描く。二分岐を基本に、角度と長さへわずかな揺らぎを加えた再帰木を候補とする。有限の描画深度に制限し、シルエットを読み取りやすくする。

「規則」と「揺らぎ」の両方が形を作ることを、技術への好奇心として表現できる。これは前半の専門領域から、本人の創作・遊びへの自然な切り替えになる。

任意操作として「別の木を育てる」ボタンを設置してもよい。操作時だけ種を変え、スクロール体験中は形を固定する。詳細なパラメーター調整は既存作品へのリンクに任せ、自己紹介ページを大きな描画ツールにはしない。

## 9. 実績とプロフィールの整理

代表実績はまず4件程度に絞り、一件につき「何をしたか / 誰に役立つか / 記事・コードなどの移動先」を示す。

1. RFC Trans: RFCの自動翻訳対訳サイト。プロトコルを読む活動につなぐ。
2. Software Design: 「乱数のひみつ」「暗号のひみつ」を連載単位で紹介。各号は詳細一覧へ。
3. TLS 1.3・暗号の実装: 実装範囲を明示し、コードと解説へつなぐ。
4. Recursive Tree Renderer: ページの木と本人の作品を結びつける。

01〜04内では短い関連リンクにとどめ、05で詳しく紹介する。同じ長文カードを繰り返さない。

活動履歴、資格、過去のゲーム・ツールなどは後半の「詳しい経歴」「すべての制作物」にまとめる。初版では開閉可能な詳細領域に既存情報を保持する案とし、件数が増える場合は一覧ページへの分離を検討する。

現在のブログ・GitHub・連絡先を引き継ぐ。仕事の受注可否や対応分野は推測で追加せず、「記事を読む」「実装を見る」「連絡先を見る」を基本導線にする。

## 10. 実装方針と確認条件

現状のGitHub Pages上の静的サイト構成を維持する方針。今回の規模では、フレームワーク導入を前提にしない。

- 内容は意味のあるHTMLで構成し、レイアウトはCSSで作る。
- 図形はCanvas 2Dを第一候補とし、説明・ボタン・作品リンクはHTMLに置く。
- 新しい演出は独立したJSへまとめる。旧ScrollMagic・TweenMax・jQuery依存は利用箇所を確認してから整理する。
- 描画は画面内かつ状態が変わる場合に限定。非表示タブでは停止し、解像度と枝数に上限を設ける。
- 画像の原本は保持。配信用の縮小WebPなどを別途作成し、下部画像と表情差分は必要に応じて読む。
- 初期転送量は暫定1MB前後を目標にし、人物画像の画質と合わせて測定する。達成済みの数値ではない。

確認条件:

- 最初の画面で名前、専門領域、主要リンクが読める。
- 主要作品・連絡先へナビから直接到達できる。
- 幅375px・390px・768px・1440px、短い画面、200%拡大で文字・人物・操作が重ならない。
- スクロールを戻す、章へ直接移動する、途中で再読み込みする場合も図形状態が破綻しない。
- 動きを減らす設定とJS無効時にも内容へアクセスできる。
- 表情の切り替えで人物がずれず、画像の読み込みでレイアウトが動かない。
- 既存の履歴・作品リンク・クレジットを取りこぼさない。

## 11. 次の作業単位

1. この設計に基づく冒頭・三つの探究・木の見た目を具体化する。
2. 中核部分だけでスクロール試作を作り、粒子から通信へつながる動きとスマートフォン表示を評価する。
3. キャラクターと代表実績を組み込み、読みやすさに合わせて演出の強さを調整する。
4. 全履歴を移行し、アクセシビリティ・画像容量・操作を確認する。
